Every backup module tells you a backup ran. That is not the same as having a backup.

The upload returned success. The file is 4 MB instead of 3.3 GB, or the transfer stopped half way, or the archive is there but unreadable. You find out on the day you need it.

So it checks, every time

After the dump is uploaded it is read back from the destination, its SHA-256 compared against what was sent, and the archive opened to confirm it really contains dump.sql and manifest.json. A run is only marked Verified when the file that came back is the file that went out. Anything else is marked Unverified — because a backup you have not checked is a backup you do not have.

Three states, not two. Green ran and was proven. Amber uploaded but could not be confirmed — that one read back 1 MB of a 3.4 MB file. Red never got off the ground.

It tells you when backups stop

Success mail trains people to ignore mail. This notifies on failure, and separately when a destination has had no verified backup inside the window you set. That second alert is the one that matters: a job that silently stopped three weeks ago looks exactly like one that never existed, right up until you need it.

Every destination, and when it last actually worked. The red row has not produced a verified backup inside its window, and the people on its alert list have already been told.

Configured once, then left alone

Each destination decides its own schedule, retention and alerting, so an hourly local snapshot and a nightly off-site copy live side by side without fighting each other.

Test the connection before you trust it, then watch the history fill in underneath.

The things that bite, handled

Retention that cannot delete your last backup

Keep the last N, or the last N days, applied after each verified run. The newest backup is excluded from deletion whatever the rules say — a lone 400-day-old archive is still the only copy you have.

Credentials not in the dump

FTP and SFTP passwords are stored encrypted at rest, so a copy of your database does not hand over the keys to where your other backups live. Handled by Odoo Credential Encryption, which this installs alongside.

A standard Odoo archive

Written with Odoo's own dump API, the same one behind Database Manager. It restores the normal way, so nothing here locks you in — stop using this module and your backups still work.

A failure cannot stop the schedule

One destination going down does not take the cron with it. Each run records what went wrong, in words, and the next destination carries on.

Where backups can go

A folder on the server — or anything mounted into it, such as an NFS share or an rclone mount. FTP and FTPS. Both need no extra Python packages.

SFTP works when paramiko is installed on the server. If it is not, the destination says so plainly instead of failing at three in the morning.

What it needs

Odoo 19

Community or Enterprise, self-hosted or Odoo.sh.

pg_dump on the server

The same requirement Odoo's own Database Manager has.

Somewhere to put them

A writable folder, or FTP/FTPS credentials. Test the connection from the form.
