The upgrade does not break on the code you remember writing. It breaks on the code you forgot.

A method that quietly stopped being called two releases ago. A view attribute that is now a hard error. An import that no longer exists. This reads your modules and tells you where they are, with the file, the line, and what to write instead.

“Deprecated” is not “safe for now”

It is tempting to treat a deprecation warning as a problem for another year. Odoo's own record says otherwise. Here is what it marked, and when it actually deleted it — taken by comparing the 17.0, 18.0 and 19.0 source trees:

API Marked Deleted Gap
tools.ignore() 16.018.0 2 releases
get_resource_path() 17.019.0 2 releases
odoo.osv.osv 17.019.0 2 releases
_flush_search() 18.019.0 1 release
check_access_rights() 18.0 still here in 19.0 overdue
group_operator= 18.0 still here in 19.0 overdue

One to two releases, every time. Which means the interesting set is not what 19.0 just deprecated — it is everything 18.0 marked that is still there. That code has run out of road, and the scanner grades it accordingly.

Three verdicts, not one list

Already removed

Gone in the release you are running. This is not a warning about the future — the module is broken now, and in the case of a view or a data file it will not even install.

Due for removal

Marked two or more releases ago and still present. On Odoo's own record that is exactly the age at which things get deleted, so this is what the next upgrade is most likely to take.

Deprecated

Marked in the current release. It still works. It will not keep working, and now is the cheap time to deal with it rather than during an upgrade weekend.

A report you can act on without hunting

Every finding carries the module, the file, the line number, the line itself, and the replacement. One sentence at the top says what to do first.

The verdict leads with what is already broken. Thirty-six calls that no longer exist outrank anything merely deprecated, so the reading order matches the fixing order.

Filter and group by module, file, severity or rule. Hand one module's list to whoever owns it.

It reads the code, it does not search the text

Python is parsed into its syntax tree; XML is parsed as XML. That is the difference between a report somebody finishes reading and one they abandon on the second page, because a scanner that cries wolf gets ignored exactly like a deprecation warning does.

A comment is not a call

check_access_rights in a docstring, a comment, an error message or a variable name is not a use of it. Searching for text cannot tell; parsing it can.

The replacement is not the problem

Domain.AND() is what you migrate to; expression.AND() is what you migrate from. Rules are pinned to the object, so code you have already fixed stays quiet.

A route is read from the decorator

type='json' matters on @route and nowhere else, so that is where it is looked for — not in a dictionary that happens to contain the same words.

Owl templates are not views

An attrs on a component under static/ has nothing to do with the one 17.0 removed from views, so that directory is left alone.

Held to its own standard: pointed at a full Odoo 19 install — 131 modules, 3,751 files — it reports five findings, and all five are real deprecated calls in that code. A scanner that returned three hundred would be telling you nothing.

Thirty-six rules, none of them invented

Every rule names the release that deprecated the API and the file and line in the Odoo source where that is declared. You do not have to take any of it on trust — open the file and look.

Run it before the module installs, not after

A module that will not install on the new version cannot be inspected as an installed module — which is precisely when you need to know what is wrong with it. So the scanner reads whatever is in your addons path, installed or not. Drop last year's modules next to a fresh Odoo, scan, and get the list before you start.

Odoo 20 is not released yet

Nobody can hand you its removal list today, and any module claiming to would be guessing. What this does is different and checkable: it finds what Odoo has already marked, grades it by how long it has been marked, and cites the source for each. When 20.0 lands the rules get updated; the ones shipped today are useful now, because the code they point at is already a problem.

What this is not

It does not rewrite your code — it tells you where to, because a bad automatic fix costs more than the finding saved. It reads Python and XML, not JavaScript. It cannot know your business logic: a method that Odoo no longer calls is reported, but whether losing it matters is your call. And a clean report means nothing deprecated was found, not that the upgrade will be painless.
