Connecting an AI assistant to Odoo is the easy part. Letting it change data is not.

A model that can read your database is useful. A model that can write to it is a decision someone has to be able to review, undo and account for — which is everything this module adds on top of the protocol.

The path a request takes

Five checks, before anything is written

Every tools/call goes through the same sequence. Any step can stop it, and whatever happens is on the record.

01
Which key is this?

A bearer token checked against res.users.apikeys, scoped to this server. Hashed by Odoo, expiring, revocable from the user form, and tied to a real user.

02
May it call this tool?

Each tool can be switched off, restricted to groups, confined to named models and capped at a number of rows.

03
Does a person need to see it?

A tool marked for approval does not execute. It parks, shows what it would have done, and waits.

04
What may that user actually touch?

The call runs as the key’s user — never as root — so Odoo’s own access rights and record rules still decide, exactly as they do in the web client.

05
Write it down.

Succeeded, failed, denied or parked — every call leaves a row with the arguments, the result and how long it took.

Approval

See the change before it happens

A parked call is replayed as a dry run first, so the request carries its own preview: the current values, and what the model wants to set them to. Approving runs it as the agent's user, not as the approver — saying yes means "let that account do this", not "do it with my rights".

The before, and the intended after. Nothing has been written. Approve and Run executes it; Reject closes it and tells the agent so.

The agent is told plainly what happened. It gets back “this needs a person to approve it, nothing has been modified, do not retry” — so it reports the wait to whoever asked instead of hammering the same call.

The record

What the AI did last Tuesday

Someone will ask. Every call is logged with the tool, the user the key belongs to, the client that connected, the model touched, the arguments sent, the number of records affected and the answer that went back — including the calls that were refused.

Four outcomes, not one. Succeeded. Failed, with the reason the model was given. Denied, because that key's user has no rights to the model. Awaiting approval.

Tools

Every tool is a record you can edit

Eight to start with: list models, describe fields, search, read, aggregate, create, update and delete. They are data, not code — so you change what the AI can do from a form, without touching Python. All three write tools ship switched off.

Turn one on when you want it, and not before. A write tool with no approval required is flagged in red, because that is worth noticing.

Narrow it as far as you like. This one may only update contacts and leads, only for keys belonging to that group, fifty records at a time, and only after a person approves. The description underneath is what the model itself is told.

Connecting

One URL and a key

Generate a key from the user's own form in Odoo, then point any MCP client at the endpoint. Streamable HTTP, so there is nothing to install next to the model and no gateway in between.

POST https://your-odoo/mdx/mcp Authorization: Bearer <the key you generated> Content-Type: application/json { "jsonrpc": "2.0", "id": 1, "method": "tools/list" }

Implements the 2025-06-18 Model Context Protocol — initialize, tools/list, tools/call and ping, with the older 2025-03-26 and 2024-11-05 versions accepted so existing clients keep working.

Built for models, not just for HTTP

The things that go wrong with AI tools, handled

A failed tool is not a failed request

Protocol problems come back as JSON-RPC errors; tool problems come back as a result the model can read. Get this backwards — as many servers do — and the model never learns why it failed, so it retries the same broken call forever.

A guessed argument is refused, not ignored

Ask to group by group_by when the tool takes groupby and you get told, by name, which arguments it accepts. Silently dropping it would hand the model one meaningless group and it would report that as the answer.

Secrets are masked before they leave

System parameters, stored passwords, SMTP credentials and API keys come back masked — including for an administrator's key, which is the case that matters, because nothing else would have stopped it. Add your own fields to the list.

A vague question cannot drag the whole table through a model

Each tool has a row cap, and the aggregate tool exists so “how many, by country” is one grouped query rather than fifty thousand records read into a context window.

Dry run on every write

Create, update and delete all accept dry_run. The call reports exactly what it would have changed and touches nothing — which is also how the approval preview is built.

Discovery that tells the truth

The model-listing tool reports only the models that key's user can actually read, so the assistant never plans around a table it will be refused at.

A key is as powerful as its user

Access rights are the real boundary here, and they are the ones you already have. Issue the key to a user with the rights the assistant should have — not to an administrator out of convenience. Masking will still cover the credential fields, but nothing can put back a permission you granted.

What this is not

It is not a chatbot and it ships no model of its own — you bring Claude, ChatGPT, Cursor or anything else that speaks MCP. It exposes the ORM, not business workflows: an agent can read and change records, but confirming a sale order is an action on that model, not a tool here. And it does not open your database to the internet by itself — the endpoint is only reachable wherever your Odoo already is.

What it needs

Odoo 19

Community or Enterprise. Depends on base and web only.

An MCP client

Anything speaking Streamable HTTP. No extra Python packages, no gateway, no sidecar.

Five minutes

Install, generate a key on a user, paste the URL. The read tools work immediately.
