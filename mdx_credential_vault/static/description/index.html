Point it at a field. That is the setup.

Any stored text field on any model. Values are encrypted on write and decrypted on read by the ORM itself, so the module that owns the field carries on exactly as before — no code changes, no re-entering credentials, nothing to integrate.

Every protected field, with a live count. How many rows are encrypted, and how many are still in the clear.

Values that predate protection keep working. They stay readable until you choose to convert them, so switching this on cannot break a running integration. The migration is safe to re-run.

How it is built

Fernet: AES-128-CBC with an HMAC

Authenticated encryption, so a tampered value fails loudly instead of quietly decrypting to nonsense.

The key never touches the database

It lives in the filesystem data directory, created on first use with owner-only permissions. A stolen dump therefore contains no way to decrypt itself, which is the entire point.

Encrypted at the ORM layer

Values are decrypted as they enter the record cache, so reading the field in Python gets the password — not just the web client.

It refuses to corrupt a secret

Ciphertext is longer than the value it replaces, so a field with a length limit is rejected rather than silently truncated.

Back up the key file

It lives in the Odoo data directory and it is not in your database backup unless you put it there. Lose the key and the encrypted credentials cannot be recovered. That is the property that makes this worth having, and it cuts both ways — so it is on the box, not in the small print.

What this is not

It protects data at rest. It is not a second permission layer: a user who can already read the field through Odoo still sees the value, because masking it would break every integration that legitimately needs it. Encrypted fields also cannot be searched or sorted on — ciphertext does not compare. Protect credentials, not fields you filter by.

What it needs

Community or Enterprise. Depends on base alone.

Self-hosted
