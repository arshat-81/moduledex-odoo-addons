Odoo tells you which groups a user is in. It never tells you what that actually means.

So you end up reading ir.model.access by hand, adding a group to see what happens, and telling a client “I think that's everything”. This app answers the three questions that actually come up.

“Why can they see that?”

You never gave them the group. Another one implies it, and Odoo wrote it onto the user as though you had.

“What breaks if I remove it?”

The honest answer is usually “let's find out on Monday”. That is a terrible answer to give the person paying you.

“Who granted this, and when?”

Odoo keeps no history of access-rights changes. When an auditor asks, there is nothing to show them.

Every permission a user really has

Pick a user, get every model they can reach with read, write, create and delete resolved the way the server resolves it. Odoo 18 writes implied groups straight onto the user record, so the user form shows one flat list of dozens of groups with no indication of which were chosen and which were inherited. This separates them again.

366 models, resolved in under a tenth of a second. Every model the user's groups unlock, with a Why? on each row. Screenshots taken on Odoo 19; the Odoo 18 build is identical apart from group terminology.

And exactly where it came from

Click any row and get the chain: the group you actually assigned, the implication path to the group that carries the access control, and the rule itself. Record rules are shown the way the server applies them — group rules OR-ed together, global rules AND-ed over the top — so you can see at a glance when a global rule is quietly narrowing everything else.

“Sales / Administrator → Sales / User: Own Documents Only.” The chain that granted it, and the global record rule quietly narrowing everything underneath. Thirteen sources on this one model alone.

Prove the change before you make it

Stage the groups you intend to add or remove and see precisely which permissions the user would gain and lose — then apply it, or throw it away. It also warns you about the things that catch people out: groups that come along for the ride, a group you cannot remove because something else implies it, and any change that quietly grants Settings access.

The preview writes nothing. Not to a savepoint, not to a temporary record, not to the user. A hypothetical group set is resolved in memory, so an abandoned preview cannot leave anything behind — there is no state to clean up and nothing to undo.

Twelve permissions gained, nothing lost — before anything is written. Draft, previewed, applied. You see the whole impact while the change is still a proposal.

Compare two users, or a plan

Put two users side by side and get a straight diff of what one can do that the other cannot. Or compare a real user against a proposed set of groups — the fastest way to answer “make the new hire like Sarah, but without the accounting.”

A new starter against an established colleague. Every model one can reach that the other cannot, and exactly which operations differ.

A history Odoo does not keep

Every change to a group, an access control or a record rule is recorded with who made it, when, and the before and after values. Module installs are deliberately excluded, so the log holds human decisions rather than thousands of rows from your last upgrade. Entries cannot be edited or deleted from the interface by anyone, including administrators.

The configuration that causes access bugs

Five checks, each decidable from the configuration alone. No heuristics, no “this looks too permissive” — a finding either holds or it is not reported.

Paths to Settings access

A harmless-looking group that transitively implies administrator. Nobody remembers creating these.

Global rules shadowing group rules

The single most common reason a permission change appears to do nothing at all.

Access controls that can never grant

A group rule sitting behind a global one that already gives everyone the same thing.

Write access without read

Surfaces to the user as an access error they cannot act on, because the record cannot be shown.

Redundant implications

A link that changes nothing, hiding the inheritance that does.

On a clean Odoo database this reports a few dozen findings, not thousands. A list nobody trusts is a list nobody reads.

A real scan of a standard Odoo database. Including a critical one: a harmless-looking group that reaches Settings access through another group, which is invisible on the user form.

Why you can trust the numbers

It agrees with the server, and that is tested

The resolver mirrors Odoo's own SQL rather than reimplementing its intent. A test asserts that the set of models it reports as readable is identical to the server's own list for the same user. If the two ever disagree, the test fails.

It does not hand out privilege

When you apply a staged change it is written with your rights, never through sudo, so every core constraint still applies. A tool that audits permissions has no business escalating its own.

It tells you when it might be wrong

If another installed module overrides Odoo's access checks, the matrix says so rather than pretending its answer is the whole story. Detected by inspecting what is actually loaded, so unknown modules are caught too.

Read-only unless you say otherwise

Resolving, comparing, previewing and scanning never change a permission. The only write is a staged change you explicitly apply — and that one is logged.

What this is not

It is not a restriction engine. It does not hide menus, lock fields or add a second permission system on top of Odoo's. It makes the permission system you already have legible, so the groups you configure are the groups you meant. If you already run a restriction module, this works alongside it and will tell you it is there.
